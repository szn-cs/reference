	- Q: What full-stack workflows degrade when the environment is optimized for persistent agent sandboxes rather than lifecycle-managed dev environments?
		- #+BEGIN_QUOTE
		  ### Full-stack development scenarios that are **problematic on Blaxel** (summary)
		  
		  These are not hard blockers, but **systemic friction points** caused by Blaxel’s persistent, agent-centric sandbox model.
		  
		  | Scenario                               | Why It’s Problematic on Blaxel                                                                                                      |
		  | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
		  | **Environment branching / rewind**     | No first-class snapshot or fork semantics; persistent sandboxes accumulate state, making “try-and-revert” workflows fragile.        |
		  | **Heavy frontend dependency churn**    | Repeated `npm/pnpm/yarn` cycles pollute state (lockfiles, caches, node_modules), reducing determinism across retries.               |
		  | **Multi-service local stacks**         | Running API + frontend + DB + workers is possible but lacks orchestration guarantees; process and port drift accumulates over time. |
		  | **Failure-prone iterative generation** | Agents must perfectly clean up broken migrations/configs; persistent state makes retries increasingly unreliable.                   |
		  | **Reproducible / auditable builds**    | Continuity over time makes it hard to guarantee identical base state and dependency graphs for repeatable builds.                   |
		  
		  **Underlying cause (one line):**
		  Blaxel optimizes for **continuous agent presence**, not **environment lifecycle reset and rollback**.
		  
		  This is why it excels at conversational, always-on coding agents—but degrades when full-stack workflows require frequent teardown, branching, or strict reproducibility.
		  
		  #+END_QUOTE
