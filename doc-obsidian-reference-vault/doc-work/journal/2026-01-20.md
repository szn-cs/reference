    - Comparing infrastructure sandboxing specifically targeting AI agents/systems applications specifically AI Coding Agents.
        - considerations:
            - microVMs preferable for supporting GTK and system-level functionality of generated code apps.
            - looking for fully-featured all-in-one sandboxing solution tailored to AI agent systems - explicitly optimized for this domain (integration with AI agent SDKs, features for file/logs streaming from sandbox and file operations, snapshots, multitenant gateways/subdomains, etc.)
            - Code generation agents need **low-latency** sandboxing with **persistent filesystems** or state. requires a persistent environment where the filesystem can be modified,  dependencies can be installed, and state is preserved across multiple interactions.
        - main elements of AI agent systems core infrastructure platform includes: sandbox hypervisor, orchestration, networking;

    - Blaxel is a new alternative to E2B but it is not open-source. Different approaches to memory management - E2B focuses on session based memory vs Blaxel on persistent memory long term continuous coding assistant (optimization for user workflow continuity). Blaxel persist view of project state for sessions even days after.
        - Blaxel maintains state indefinitely (**perpetual sandbox**) while E2B destroys sandbox after 30 days (temporary sandbox).
        - > | Aspect of statefulness | **Blaxel**                        | **E2B**                         | Short explanation                                                        |
          > | ---------------------- | --------------------------------- | ------------------------------- | ------------------------------------------------------------------------ |
          > | State model            | **Paused / resumed environments** | **Session-scoped environments** | Blaxel keeps environments parked; E2B keeps them alive only while active |
          > | Memory state           | **Preserved**                     | **Not preserved**               | Blaxel resumes RAM state; E2B restarts processes                         |
          > | Process continuity     | **Yes**                           | **No (after session end)**      | Blaxel keeps running processes across pauses                             |
          > | Filesystem state       | Yes                               | Yes                             | Both persist generated files and artifacts                               |
          > | Resume semantics       | **Resume**                        | **Restart**                     | Blaxel continues; E2B rehydrates                                         |
          > | Resume latency         | **~25 ms**                        | ~150–200 ms                     | Memory resume vs environment restart                                     |
          > | Agent loop impact      | Minimal overhead                  | Overhead per interaction        | Latency compounds in iterative agents                                    |
          > Summary:
            - Blaxel provides true stateful execution (memory + process continuity preserving execution context not only data). Sandbox machines sleep with full memory state restored instead of reboot.
            - E2B provides session-level statefulness (filesystem persistence without memory continuity).

      [[2026-01-23]]
        - Choosing Google Agent Sandbox standard for Kubernetes will require a lot of custom implementations for SDK features equivalent to E2B tailored for AI coding agents - such as api for file operations in the sandbox (running the generated code) to be controlled by the ai agent instance (which is running inside its own sandbox), file streaming functionality, snapshots and persistence;
        - ==E2B== has Full OS access (shell, filesystem, browsers). better if no-code platform needs to run large toolchains, build pipelines, or dev-style workflows. Has richer tooling.
        - Reconsider Blaxel once it matures.
        - Blaxel actually can provide competitive advantage when adopted because of its perpetual sandboxes that do not require a clean startup and compilation of project. In addition to extremely low startup times.
          [[2026-01-24]]
            - ==Blaxel== is more attractive because of its indefinite standby and full sandbox state snapshots. The only downside is that it is not opensource. while E2B can be hosted on BYOC GCloud.
        - [[2026-01-25]]
            - For the Rust Tauri apps, high security model of MicroVMs is required - ==Firecracker==
            - For long agent sessions and persistent state with instant startups and with robust state persistence features - ==Blaxel==.
